- [x] 1.1 New migration: `export_my_data()` — `security definer`, `auth.uid()` required, returns `{ profile: {...}, participants: [...], answers: [...] }` for the caller only — verify `tools/db` tests: a happy path returning the caller's own profile/participants/answers; a second identity's export never contains the first's data; rejects an unauthenticated call.
- [x] 1.2 Same migration: `delete_my_account()` — `security definer`, `auth.uid()` required, clears `profile.display_name`/`email`, sets `deleted_at`, rewrites every one of the caller's `participant.display_name` rows to a fixed placeholder (design.md D1 — `profile_id` unchanged) — verify `tools/db` tests: profile fields cleared and `deleted_at` set; participant display names rewritten across multiple events; a participant's score rows (`step_result_participant`/`event_final_participant`) are untouched; two different deleted accounts who both played the same event both succeed without a constraint violation (the scenario D1 exists to avoid); idempotent on a second call.
- [x] 1.3 Same migration: `purge_expired_anonymous_participants()` — deletes every anonymous participant of an event whose `ended_at < now() - interval '90 days'`, nulling `team.captain_participant_id` first where needed (design.md D3), returns the count purged; granted to no client-facing role — verify `tools/db` "time-travel" tests: an anonymous participant of an event ended 91 days ago is purged, along with their `answer`/`step_result_participant`/`event_final_participant` rows; an anonymous participant of an event ended 89 days ago is untouched; an account-holding participant of an event ended 91 days ago is untouched; a purged participant who was a team captain doesn't block the delete and the team's `captain_participant_id` ends up null.
- [x] 1.4 Same migration: `create extension if not exists pg_cron` + `cron.schedule(...)` registering `purge_expired_anonymous_participants()` on a daily schedule (design.md D2) — verify via `supabase db query` directly (not a `tools/db` vitest test: PostgREST only exposes `public`/`graphql_public` locally — `cron.job` isn't reachable through the same client the test suite uses), asserting the job is registered with the expected command and schedule. **Result**: `select jobname, schedule, command, active from cron.job where jobname = 'purge-expired-anonymous-participants';` → `{active: true, command: "select public.purge_expired_anonymous_participants();", jobname: "purge-expired-anonymous-participants", schedule: "0 3 * * *"}` — registered as expected after a fresh `supabase db reset`.
