## 2. `apps/party`: `mc:reveal`

- [x] 2.1 `mc:reveal` handler: `requireController` gate; rejects `not_locked` when there is no current step or it isn't `locked` (design.md D3) — verify tests for both rejections.
- [x] 2.2 Fetch the step's scoring config (`points_correct`, `team_award_points` from `step`; `correct_option_id` from `game_mcq`), the event's full participant roster (`id`, `team_id`, `display_name`), and this step's `local_answer` rows; run `scoreStep` — verify a test asserting the computed result matches hand-calculated expectations for a small fixture (mirrors a fixture used in packages/shared's own tests, but exercised through the real DO/Postgres path).
- [x] 2.3 Persist-then-transition (design.md D4): a small retry-with-backoff helper (3 retries after the first try, 200/400/800ms backoff — `apps/party/src/retry.ts`'s `withRetry`, generic and unit-tested in isolation) wraps the Postgres flush — `answer` rows (real `is_correct`/`scored_points`, using `local_answer.id` as `receipt_seq`), `step_result_participant`/`step_result_team` rows (all via `upsert` so a retry after partial success is safe), and `step.status = 'revealed'` in Postgres — only after which the DO's own `RoomState.step.status` becomes `revealed` and a broadcast happens; on exhausted retries, send `reveal_failed` to the controller and leave the step `locked` (no state mutation, no broadcast). **Test approach note**: the "fails once, succeeds on retry" case is verified as a pure-function unit test of `withRetry` itself (`apps/party/test/retry.test.ts`, injectable fake) rather than forcing a real transient Supabase network failure — there's no seam in this project's "real Supabase, no mocking" integration harness to make ONE specific real network call fail on attempt 1 and succeed on attempt 2 within a single command's retry loop. The "every retry fails" case, however, **is** a genuine EventRoom-level integration test: a participant's Postgres row is deleted out from under their already-accepted `local_answer` between `mc:lock` and `mc:reveal` (a real, deterministic, persistent foreign-key violation on every attempt — not a mock), asserting `reveal_failed`, the step staying `locked` in both Postgres and the DO's own persisted state, and nothing broadcast to another connected client.
- [x] 2.4 Broadcast `step_results` (per-participant/team, no answer-key leak) and a fresh `rankings` (queried from all of the event's `step_result_participant`/`step_result_team` rows so far, competition-ranked per design.md D5) to every connection; send each player a private `own_result` (every player gets one, not only submitters — a non-submitter's is `{isCorrect: false, points: 0}`, matching SPEC.md's `own_result` being addressed "to a single player," i.e. individually, not "only to answerers") — verify a test asserting the broadcast shape (and that no `correct_option_id`/`optionId` of the correct answer appears via `JSON.stringify`), and a test asserting each player's `own_result` correctly reflects their own outcome, submitter or not.
- [x] 2.5 A repeated `mc:reveal` on an already-`revealed` step is a no-op (no recomputation, no re-broadcast) — verify a test.
- [x] 2.6 Late-joiner scoring (design.md D1): a participant created after step 1 is revealed has no result row for step 1 and scores normally on step 2 — verify a test (this is the FR-056 verification; no dedicated eligibility code should exist to test around, only the emergent behavior).
