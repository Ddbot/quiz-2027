## 3. `apps/party`: full command-surface tests for the new role/command

- [x] 3.1 A `screen` connection receives the public broadcasts (`state`, `step_results`, `rankings`) identically to an admin connection, and never receives an `own_result` (that stays player-private, unaffected by this milestone) — verify a test.
- [x] 3.2 A live 3-connection scenario (admin/controller, screen, player) exercises `mc:start` → `answer:submit` → `mc:lock` → `mc:reveal` → `operator:display` end to end, asserting the screen connection's received messages have everything needed to render each of the 7 views without further requests — verify one integration test covering this full path. **Harness finding**: `mc:reveal` fires 3 synchronous broadcasts back-to-back (state/step_results/rankings) after real async I/O with no yield in between; the shared `waitForMessage` helper's per-call `{once: true}` listener pattern can race and lose messages dispatched before it re-subscribes between them (observed directly: two of three messages went missing on the screen connection specifically). Fixed by adding a queue-backed reader (`queueMessages`, this task's test only — the existing `waitForMessage`/`waitForMessageOfType` helpers and every test using them are untouched, since they've worked reliably for single-message-at-a-time waits) that attaches one persistent listener up front and buffers, immune to dispatch-order timing regardless of how tightly multiple broadcasts are sent.
